# Product & Engineering Roadmap

Phasing is scoped so every phase ships something real and testable end-to-end, rather than shallow-stubbing all modules at once. Each phase builds on the multi-tenant/RBAC/audit foundation from Phase 1 — no phase requires re-architecting an earlier one.

## Phase 0 — Foundation Docs *(this pass)*
SRS, HLD, LLD, ER diagram, API contracts, roadmap. No code.

## Phase 1 — Platform Core *(this pass)*
- Repo scaffold (backend/frontend/docker/docs/scripts), clean architecture layers
- PostgreSQL schema + Alembic migration for: company, department, user_account, employee, role, permission, role_permission, user_role, audit_log
- JWT auth (login/refresh/logout/forgot-password/reset-password/verify-email), Redis-backed refresh-token rotation & denylist
- Dynamic RBAC engine + 5 seeded default roles per company + permission-matrix admin UI
- Company management (Super Admin), Department CRUD, Employee CRUD — fully wired UI → API → DB
- Audit logging on all mutations
- Super Admin, Admin, HR, Manager, Employee, Finance dashboards: shell + role-aware nav (Employee/Admin/Super-Admin dashboards get real KPI widgets; others get placeholder widgets ready for their module's data)
- Docker Compose (Postgres, Redis, MinIO, backend, frontend, Nginx), GitHub Actions CI (lint, type-check, test, build)
- Seed script: 2 demo companies, users per role, departments
- Backend unit + integration tests incl. a dedicated cross-tenant-isolation test suite

**Role reassignment for existing employees (added post-ship, direct user request)**: `role_ids` was only ever accepted at employee-creation time — there was no way for an Admin to change which role(s) an *existing* employee holds afterward (e.g. to grant the Admin role to a specific employee), even though the underlying `user_role` join table always supported a user holding multiple roles at once. Added `PUT /employees/{id}/roles` (full replace, not additive) gated on `role.update` specifically — not the broader `employee.update` HR also holds, since granting Admin rights is materially more sensitive than editing a profile field. Guards against removing the company's last remaining Admin (`422`, not a silent lockout). The existing Roles checkbox UI on the Employee form (previously create-only) now also appears in edit mode, gated on the same `role.update` permission.

**Dashboard rework (added post-ship, direct user request)**: the original dashboard's "Headcount by Department" bar chart was shown to everyone (Employee included) and every role got the same company-wide "Active Projects" count gated on `project.view` — which Employee doesn't hold, so Employees never saw any project information on their dashboard at all, despite the Projects page itself already having a "my projects" self-service view since Phase 3. Reworked to: "Headcount by Project" replacing "Headcount by Department," gated Admin-only (reusing `company.configure` — the same permission that already gates the Integrations page — as the established "Admin-only settings/insight" signal, rather than inventing a new permission for one chart); a "My Projects" widget for whoever lacks `project.view` (mirrors the existing self-service-fallback pattern the Leave/Timesheet widgets already use); a "New Hires (Last 7 Days)" widget using the existing `joining_date`; and a "Birthdays This Week" widget. The last one needed a new nullable `Employee.birth_date` field — sensitive PII this app never collected before, cut from Phase 7c's digest reminders for exactly that reason — added here as fully optional (Admin/HR-settable, blank by default, employees with it unset simply never appear in the widget) since the user explicitly asked for it this time. `EmployeeSummaryResponse` gained `joining_date`/`birth_date` (previously detail-response-only) so the dashboard can compute these from the employee list it already fetches, no new endpoint.

**Configurable timesheet reminders (added post-ship, direct user request)**: extends the existing daily digest job (Phase 7c's `celery-beat`/`run_daily_digest`) with a new opt-in check. Two new fields on `timesheet_period_config` (same Settings tab as everything else timesheet-related): `reminder_enabled` (off by default) and `reminder_after_days`. Unlike the document-expiry digest (fires exactly once, by design, to avoid spam), this one is intentionally designed to **repeat every day** the condition holds — an employee whose most recent submission has gone stale past the threshold gets an email + in-app notification daily until they submit again, per the user's explicit "trigger until he sends the timesheets" ask. Reuses the existing in-app notification feed and the existing Celery email-task pattern, and — since outbound webhooks already fire from the shared `notification_service.notify()` path (Phase 7c) — also posts to Slack/Teams for free if a company has that configured, with no extra work.

## Phase 2 — Onboarding & Documents *(shipped)*
- `document_type` (per-company configurable checklist), `employee_document`, `onboarding_invite` tables; `employee.onboarding_status` (`invited → submitted → hr_approved → completed`)
- Admin-configurable document checklist (required/optional, ordered) — no code changes needed to add a document type
- Secure onboarding link: opaque token (SHA-256 hashed at rest, 7-day expiry), emailed to the new hire, resolves to a public (unauthenticated) onboarding portal
- New hire sets their password and uploads each required document via the public link; account stays deactivated (`is_active=False`) until Admin approval — the employee cannot log in through the normal flow before then
- Auto-advance to "submitted" once a password is set and every required document has been uploaded (no separate submit button/endpoint)
- HR review queue: per-document approve/reject with notes, then a `hr-approve` gate requiring every required document be approved
- Admin final approval activates the account (`is_active=True`, `is_verified=True`)
- Document storage: MinIO/S3 via boto3, presigned download URLs, content-type/size validation
- Dedicated `onboarding` permission module (`view`/`review`/`approve`/`configure`) wired into the same dynamic RBAC engine from Phase 1, including retroactive grants to companies seeded before this phase shipped

**Simplified from the original scope** (deferred, not blocking): no separate "onboarding template" or per-employee task checklist beyond the document list itself; no virus-scan integration (hook point not yet added).

**Removed after shipping** (direct user request): offer letter PDF generation/download shipped in this phase gated on `employee.view`, but that permission is company-wide by design (like every other `.view` permission in this app — see Phase 1), so any Employee-role user could browse the directory and download *any* other employee's offer letter, not just their own. Rather than bolt on one-off "self only" scoping for this single endpoint, the feature was removed outright (route, PDF service, ReportLab dependency, frontend button all deleted) rather than kept behind a narrower fix — it wasn't load-bearing for anything else and the simplest correct fix was to not have it.

## Phase 3 — Projects & Employee Mapping *(shipped)*
- `project` (name, client_id, budget, billable flag, start/end date, status) — **no** `department_id`: cross-functional projects aren't pinned to a single department
- `project_member` (project_id, employee_id, role_on_project: `manager`/`member`) — a project can have more than one manager, so this is a join table rather than a single `project.manager_id` column; a pure join table like `role_permission`/`user_role` from Phase 1, no `company_id` or RLS of its own — tenant isolation comes from always resolving the project (company-scoped) first
- `client` — lightweight (name, contact name/email/phone), managed from a "Clients" tab on the Projects screen (same tabbed pattern as Onboarding's Review Queue / Document Checklist), reusing the existing `project.*` permissions rather than a separate module — it's an assignment target for projects, not a CRM
- Full CRUD + member add/remove, tenant isolation, and RBAC tests, same rigor as Phase 1/2
- `GET /projects/mine` — self-service, any authenticated employee sees only projects they're a member of (with their role on each), independent of the `project.view` permission — matches the original spec's "View Assigned Projects" for the Employee role, and keeps budget/client data out of a plain employee's view. The frontend routes `/projects` to the full management screen or this read-only view automatically based on permission.
- Dashboard: an "Active Projects" KPI added to the existing tenant dashboard — **not** hours or cost-incurred, since neither has a real data source until Phase 4 ships; those widgets land there instead of being built against fake numbers now

**Adjusted from the original scope** (see the scope-review discussion before this phase started): the original draft asked for an "hours, cost, status" dashboard and a single `manager_id`/employee-mapping model. Both were cut back — hours/cost data doesn't exist without Timesheets (Phase 4), and a join-table `project_member` with a role flag is more correct than a single manager column since a project can have multiple managers. Employee mapping itself (multiple projects, one manager/HR/department/cost-center) was already schema-supported since Phase 1; this phase is where it got a UI.

## Phase 4 — Timesheets
- `timesheet_period_config` (per-company period type: daily/weekly/monthly, plus week-start-day for weekly) — bi-weekly and fully custom periods are deferred, not enough real-world demand to justify the extra date-math complexity now
- `timesheet_entry` (employee, date, `project_id` validated against that employee's `project_member` rows from Phase 3, hours, billable flag, work type, description) — one row per day/project
- `timesheet_submission` — groups an employee's entries for one period and carries the actual workflow state (`draft → submitted → approved/rejected`); approval happens per period, not per entry row
- Approval chain: Manager approval always required (every employee already has one); a per-company toggle adds an optional final Finance sign-off. "Project Manager" as a distinct configurable step is deferred — Phase 3's `project_member.role_on_project` makes it possible to add later without a schema change, but a fully generic N-step engine isn't worth the complexity for the first version
- Rule engine: min/max hours per day, duplicate prevention (unique employee+date+project), weekend-logging warning (day-of-week only, no calendar dependency — holiday-aware rules wait for Phase 5's `holiday_calendar`), lock on approved periods with Admin-only reopen, bulk-approve. Project is always required (structural); description is optional by default with a per-company toggle to require it (`timesheet_period_config.require_description`, migration 0005 — flipped from the initial mandatory-by-default so employees can log time first and fill in detail later, not before)
- My Timesheet UI is a full month calendar (not a flat list): the active submission period is outlined inside the month for context, clicking a date inside it opens the log-time dialog and saves it as a draft immediately — the calendar tab is for logging only, it has no submit action
- Submission ranges are free-form, not snapped to `timesheet_period_config`: a **Drafts** tab lets the employee pick any From/To range, review every entry in it (status, rejection reason, edit/delete while still draft/rejected), and submit exactly that range — `timesheet_period_config`'s period type still drives the rule engine and the dashboard's "late" calculation, it just no longer locks submission to one window, so newly-logged entries can always be submitted by picking a range that covers them even if it overlaps something already submitted
- A **My Submissions** tab (every employee) shows the caller's own submission history in Pending / Approved / Rejected sub-tabs; the Approvals queue (for whoever holds `timesheet.approve`) uses the same three-bucket pattern instead of a status dropdown, and gained a per-row **Reopen** action (Admin-only, in the Approved bucket) so approved-in-error submissions don't need a database fix
- Permission fixes carried over from the Phase 1 catalog: Admin gains `timesheet.create`/`timesheet.export` (was missing), Finance gains `timesheet.approve` (needed for the optional Finance sign-off step) — no new permission module, reuses the `timesheet.*` catalog already seeded in migration 0001
- Timesheet dashboard: pending, rejected, late, hours by project/employee, billable %; a dedicated export panel filters CSV output by date range, project, employee, and employee location (opens in Excel, no new dependency) — a formatted `.xlsx`/PDF report is a fast-follow, not blocking this phase
- `employee.location` (nullable, migration 0006) — set at employee creation for a multi-country workforce (e.g. United States / India) specifically so exports can be filtered by it; not a DB enum, same loosely-validated-string pattern as `employment_type`/`status`, so adding a third country later needs no migration
- Reminders (late submission, pending approval) are deferred to a fast-follow once the core flow ships — no scheduler (`celery-beat`) service exists yet, and standing one up before the thing it reminds about is proven isn't worth the added infra now

**Adjusted from the original scope** (see the scope-review discussion before this phase started): the original draft specified a fully configurable Employee→Manager→PM→Finance chain and holiday-aware rules with no holiday table to back them. Both were narrowed — a 2-tier Manager+optional-Finance chain covers the vast majority of real approval flows without a generic workflow engine, and weekend/holiday rules were split so the calendar-dependent half waits for Phase 5. Submission was modeled as period-level (not per-entry) since that's how the rest of the draft's language ("period rules", "late submission") already assumes it works.

**Adjusted after first use, round 1** (direct user feedback once the calendar UI shipped): entries logging and period submission were split into two tabs (Calendar for input, Drafts for review-and-submit) instead of one combined screen, description was made optional by default (see migration 0005 above), and the export gained project/employee/date-range/location filters — which is also why `employee.location` exists.

**Adjusted after first use, round 2** (feedback after trying to log time into an already-submitted period and getting blocked): submission moved from "one fixed period per company config" to a free-form date range chosen at submit time, since the entry-level `submission_id` tracking already made overlapping ranges safe — the fixed-period model was adding a restriction the underlying data model didn't actually need. Self-service submission history (My Submissions) and the bucket-based Approvals restructuring shipped in the same pass since both came from the same request.

**Bug fix after round 2** (round 2 didn't fully fix it): `create_entry` still blocked logging a *new* entry on any date that fell inside an *approved* submission's date range, even if that specific date never had an entry in it — e.g. approve a Mon–Sun submission that only actually had a Monday entry, and Tuesday–Sunday were now permanently unloggable. That check scanned date ranges instead of specific entries; removed it entirely; locking now only applies to editing/deleting an entry that is *itself* already part of an approved submission (already correctly enforced in `update_entry`/`delete_entry` and unaffected by this fix). Same fix applied on the frontend: the calendar's per-period `isLocked` gate (which relied on the same now-defunct exact-range-match assumption from the pre-free-form model) was removed in favor of gating each entry chip by its own status.

**Manager-hierarchy approval restriction (added post-ship, direct user request)**: the Manager approval step was, until now, gated only on holding `timesheet.approve` broadly — any Manager, Admin, or Finance user could approve/reject *any* employee's submission company-wide, not just their own reports. Notifications already routed correctly to the specific `employee.manager` (Phase 7b), but the actual approve/reject action didn't check that relationship. It now does: only the submitting employee's assigned manager (`employee.manager_id`) may act on the Manager stage; whoever holds `timesheet.configure` (Admin) retains an override for edge cases (manager away, chain broken, no manager assigned at all). Since a Manager is themselves an employee, their own submissions now correctly route to *their* assigned manager rather than to any Manager-permission holder — the exact chain the user asked for falls out naturally from the existing `employee.manager_id` self-reference, no new field needed. The optional second Finance stage is untouched (still company-wide by design, a compliance step not a reporting-line one). Known gap not addressed this pass: the approval *queue* (`GET /timesheets/submissions`) still lists every company-wide pending submission to any `timesheet.approve` holder, so a Manager can still see a submission outside their reporting line in the list and gets a clear `403` (not a silent failure) only when they try to act on it — filtering the queue itself to "my reports only" is a reasonable follow-up, not done here to keep this change scoped to the approval action itself.

## Cross-Phase — CSV Export (Employees, Departments, Projects, Clients)
Requested directly by the user after Timesheets shipped its export panel ("admin should have export in every module, with dates and multiple filters"). Rather than a new phase, this extends the export pattern already proven in Phase 4 to the other list-bearing modules:
- **Employees**: filters on search, department, status, employment type, location, manager, and a `joining_date` range. Gated by `employee.export` — already reserved in the Phase 1 catalog and already granted to Admin/HR, so no permission changes needed there.
- **Departments**: filters on search, parent department, and a `created_at` range (no better date field exists on the model). Required adding `department.export` to the catalog (it didn't exist before) and granting it to Admin.
- **Projects**: filters on status, client, billable flag, and a `start_date` range. `project.export` was already reserved in the Phase 1 catalog but — a real gap found while building this — **never actually granted to Admin**, so Admin couldn't have exported projects even after this ships without the fix. Migration 0007 grants it retroactively.
- **Clients**: reuses `project.export` (same permission-sharing pattern as the rest of the Clients module since Phase 3), filtered by search and a `created_at` range.

All four share the CSV-building helper (`app/utils/csv_export.py`) that Timesheets' export was refactored to use too, rather than four more copies of the same `csv.writer` boilerplate. Scope was deliberately kept to CSV with server-side filters (no `.xlsx`/PDF, no saved filter presets) — same reasoning as Timesheets' export: ship the real, useful version now, formatted reports are a fast-follow if asked for.

## Phase 5 — Leave Management *(shipped)*
- `leave_type` — per-company configurable (name, paid/unpaid, annual quota, max carry-forward days, requires-approval, requires-attachment) — merges the original draft's separate `leave_type` + `leave_policy` into one flat table, same pattern as `document_type` (Phase 2) and `timesheet_period_config` (Phase 4): no separate policy-versioning system for a first version
- `leave_balance` (employee, leave_type, year) — ledger fields (opening, accrued, carried-forward, used, adjustment) rather than a single mutable counter, so it stays encashment-ready and auditable the way Timesheets' entry-level tracking is
- `leave_request` (employee, leave_type, start_date, end_date, reason, optional attachment via the existing Phase 2 S3/document infra, status) — full-day / date-range only; half-day and hourly leave are deferred (see below)
- `holiday_calendar` (per-company: date, name, optional `location`) — also closes the loop Phase 4 left open: Timesheet's weekend-warning rule becomes holiday-aware once this table exists. `location` is nullable and defaults to company-wide; when set (e.g. `"India"`), the holiday only excludes a business day and only appears on the calendar for employees whose `employee.location` matches exactly *(location added post-ship, migration 0009, once Admins needed region-specific public holidays for a multi-country workforce — see API_CONTRACTS.md)*
- Approval chain: Manager always required, with a per-company toggle for an optional final HR sign-off — the same simplified 2-tier shape that worked for Timesheets (not literally shared code; Leave and Timesheets are different entities), and it matches the permissions Manager/HR/Admin already hold since Phase 1 (`leave.approve`/`leave.reject`)
- Balance enforcement: a request is rejected at creation time if pending + approved requests would exceed the available balance — avoids needing a hold/release state machine for "reserved" leave
- Carry-forward: a manual Admin-triggered action (per employee or company-wide) at the year boundary, not an automatic scheduled job — no `celery-beat` introduced this phase, consistent with Phase 4 deferring the same for reminders
- Leave calendar: extends the hand-built calendar component Timesheets already shipped (multi-day leave spans + holidays) rather than adding FullCalendar as a new dependency
- `leave.export` permission + CSV export (date range, leave type, employee, status filters) shipped from the start, applying the cross-module export pattern (Employees/Departments/Projects/Clients/Timesheets) at build time instead of retrofitting it afterward
- Permission fix: `leave.create` added to Admin/HR defaults so they can file leave on behalf of an employee (e.g. recording sick leave after the fact) — currently only Employee has it
- Dashboard: the existing "Leave" placeholder card becomes real (pending leave approvals, who's on leave today)

**Adjusted from the original scope** (scope-review discussion before this phase started): half-day and hourly leave were cut to full-day/date-range only — half-day is a real, common need but was cut anyway this round in favor of shipping the simpler model first; hourly leave specifically needs a work-day-length baseline that doesn't exist until Attendance/shift management (Phase 9), so building it now would mean assuming a placeholder number. The leave calendar reuses Timesheets' hand-built component instead of adding FullCalendar, and carry-forward is a manual Admin action rather than a scheduled job, both to avoid new infrastructure (a JS calendar library; `celery-beat`) for a first version. "Reuses the Phase 4 configurable-chain engine" from the original draft was inaccurate to keep — Phase 4 never built a generic reusable engine, it shipped a simplified Manager+optional-second-approver *pattern*, which Leave now follows on its own terms (Manager + optional HR, vs. Timesheets' Manager + optional Finance).

**Manager-hierarchy approval restriction (added post-ship, direct user request)**: identical change to the one made to Timesheets (see Phase 4) — the Manager approval step now requires being the requester's specifically-assigned manager (`employee.manager_id`), not just any `leave.approve` holder company-wide. Whoever holds `leave.configure` (Admin) retains an override. A Manager's own leave requests route to *their* assigned manager, the same self-referencing chain Timesheets now uses. The optional HR stage is untouched. Same known gap as Timesheets: the approval queue itself isn't filtered to "my reports," only the approve/reject action is restricted.

## Phase 6 — Assets *(shipped)*
- `asset_type` (per-company: name) — a simple catalog, same pattern as `document_type` (Phase 2) and `leave_type` (Phase 5): no separate category-hierarchy system for a first version
- `asset` (asset_type, asset_tag/serial number, name/label, purchase_date, warranty_expiry, status, notes) — `status` is `available | assigned | retired | lost | damaged`, kept in sync automatically by assign/return, but directly editable for `retired`/`lost`/`damaged` since those aren't assignment events
- `asset_assignment` (asset, employee, assigned_at, assigned_by, returned_at, returned_by) — a ledger, not a single mutable "current holder" field on `asset`, same "compute from source records" approach as Timesheets' entry status and Leave's balance ledger; "who has this asset now" and "history per employee" both fall out of querying this table. At most one open (`returned_at IS NULL`) assignment per asset at a time, enforced at the service layer (mirrors Leave's overlap-prevention check)
- Assignment/return: Admin/HR act directly — no approval step, no request/queue workflow (unlike Timesheets/Leave, which both have one). Assigning a non-`available` asset, or returning one with no open assignment, is rejected
- Warranty tracking: `warranty_expiry` is a plain nullable date, shown in the asset list/detail — no expiry alerts or notifications this phase (that needs a notification mechanism, which is Phase 7)
- No Onboarding (Phase 2) hook — Assets stays a fully separate module this phase; equipment issuance isn't part of the onboarding checklist
- Permissions: `asset.view/create/update/delete/export` — Admin gets all; HR gets view/create/update/export (assign/return are just `update` actions, not a separate permission, matching "Admin/HR act directly"); Manager gets view-only (same broad-company-view default every other module gives Manager); Employee/Finance get no company-wide grant, but can always see their own currently-assigned assets via a self-scoped `/assets/mine`-style endpoint that needs only authentication, the same self-scoping pattern as `/leave-requests/mine` and `/timesheets/entries`
- Deleting an `asset_type` with any assets against it, or an `asset` with any assignment history, is blocked (`409`) rather than cascading — same pattern as `leave_type`/`project`
- `asset.export` CSV (asset tag, type, status, current holder, purchase/warranty dates), filterable by type/status/employee, shipped from the start — same cross-module export pattern as every prior phase
- Asset counts (total/available/assigned/retired) surface as summary stats inline on the Assets list page rather than a separate Dashboard tab — lighter-weight than Timesheets'/Leave's Dashboard tabs, matching this phase's simpler no-approval-chain shape; revisit if Assets grows enough to warrant its own tab later

## Phase 7 — Reporting *(shipped)*
- `saved_report` (per-company: name, module, filters as JSONB, created_by) — a *saved filter set*, not a generic query builder: no arbitrary joins/group-bys/column picking. Each of the six reportable modules (Employee, Department, Project, Timesheet, Leave, Asset) already has a fixed column set and a filter-driven CSV export from its own phase — this phase adds a cross-module hub on top of that existing machinery rather than inventing a second one
- Every module's existing `export_csv` service method was split into `report_rows(...) -> (header, rows)` + a thin `export_csv` wrapper around it, so the new Reports hub reuses the exact same query/row-building logic (and therefore the exact same filters and column sets) that module's own Export button already used — zero duplicated SQL
- `POST /reports/preview` runs any module's filters ad hoc (without saving) and returns up to 200 rows on-screen plus a `total`/`truncated` flag, so a report can be reviewed before committing to a full CSV download — previously every export was a blind download with no on-screen preview anywhere in the app
- `saved_report` CRUD lets a name + module + filter combination be persisted and re-run later (`POST /reports/{id}/run`) or exported (`GET /reports/{id}/export`) without re-entering the filters; saved reports are company-shared (visible to anyone with `report.view`), not private to their creator, same as Leave types/holidays
- Permissions: `report.view/export` already existed as an unused catalog stub since Phase 1 (Admin/Finance: view+export; HR/Manager: view-only; Employee: none) — this phase adds `report.configure` (create/update/delete saved reports), granted Admin-only, matching the `leave.configure`/`timesheet.configure` precedent of keeping "manage shared definitions" narrower than "use them"
- No pagination added to the underlying per-module queries — preview and export both run the same unpaginated `report_rows()` query and preview just truncates the in-memory result to 200, which is fine at this app's scale but would need real pagination if a module's row count grew large

**Adjusted from the original scope** (scope-review discussion before this phase started): the original draft bundled Reporting with Notifications (in-app WebSocket notifications, digest reminders, Slack/Teams webhooks) — split apart because Notifications needs infrastructure that doesn't exist yet (a real-time channel, a job scheduler for digests, outbound webhook integrations), while Reporting is a straightforward extension of patterns already shipped in every prior phase. Notifications now has its own phase (7b, below) so it isn't blocked behind Reporting shipping first, and vice versa. "billing, utilization, bench" were dropped from the reportable-module list in the original draft — there's no billing/utilization/bench data model anywhere in the app yet (billing lands in Phase 9 too, and utilization/bench were never scoped as their own entities), so a report module for data that doesn't exist would just be an empty screen; Employee/Department/Project/Timesheet/Leave/Asset are the six modules with real data to report on today. "Column sets" (picking which columns appear) were cut from the saved-report definition — each module's report reuses that module's existing fixed export column set rather than adding a column-picker UI, keeping this phase about the filter/preview/save loop rather than a general-purpose report designer.

## Phase 7b — Notifications *(shipped)*
- `notification` (company_id, user_id [recipient], type, title, body, entity_type, entity_id nullable, is_read, created_at) — a persisted per-user feed; the REST API is the source of truth, a WebSocket connection just pushes live updates on top of it
- Delivery: a native FastAPI WebSocket endpoint (`/ws/notifications`), authenticated via the existing JWT (passed as a query param on the handshake, since a WebSocket upgrade request can't carry an `Authorization` header) — not Socket.IO, which would add a new dependency on both ends for room/fallback-transport features this app doesn't need at its current scale
- An in-process connection registry (`user_id -> open WebSocket connections`) broadcasts to whichever of that user's tabs/devices are currently connected; no Redis pub/sub this phase — the backend runs as a single Docker Compose instance today, so cross-instance fan-out isn't a real problem yet (revisit if/when the backend is horizontally scaled)
- Trigger points wired into existing services (not a generic "subscribe to any event" system): Leave (submitted → notify the approver chain; approved/rejected → notify the requester; filed-on-behalf-of → notify the employee it was filed for), Timesheet (submitted → notify approver; approved/rejected → notify submitter), Assets (assigned → notify the employee), Onboarding (documents submitted → notify the HR review queue)
- Frontend: a notification bell in the top bar with an unread-count badge, a dropdown feed (mark-as-read on click, "mark all read"), and a live WebSocket subscription that appends new notifications without polling
- No new permission catalog entries — notifications are always self-scoped to the recipient, the same self-scoping pattern as `/leave-requests/mine`

**Adjusted from the original scope**: split further from the original "Notifications" stub — digest reminders (birthdays, anniversaries, probation, document expiry) need `celery-beat`, a recurring job scheduler that doesn't exist in this app yet (a new Docker Compose service, not just new application code), and Slack/Teams outbound webhooks are an independent integration surface with their own config surface (per-company webhook URL, which events trigger it). Both move to Phase 7c so this phase can ship a real, working in-app notification system end-to-end without being blocked on scheduler infrastructure it doesn't strictly need.

## Phase 7c — Digest Reminders & Outbound Webhooks *(shipped)*
- A new `celery-beat` Docker Compose service (Celery's scheduler process) with a persisted schedule-file volume (`celery_beat_data`), so restarting the container doesn't risk re-firing a digest that already ran today
- One daily digest task (`run_daily_digest`, 08:00 UTC) that iterates every active company (setting tenant context per company, the same defense-in-depth RLS pattern every request already relies on), covering two reminder types:
  - **Work anniversaries** — employees whose `joining_date` month/day matches today, excluding their hire year (so the hire day itself isn't a false "0-year anniversary"), get a self-scoped `employee.anniversary` notification, the same feed Phase 7b already shipped
  - **Document expiry** — `employee_document` gains a new nullable `expiry_date` column (settable optionally during HR review, e.g. for a visa or ID card); a document notifies everyone holding `onboarding.review` exactly 7 days before its expiry date — an exact-date match rather than a rolling window, so a given document fires once, not once a day for a week
- Digests reuse the existing in-app notification feed rather than a separate email-digest template system — a digest is really just a notification with a scheduled trigger instead of an event trigger, so no new delivery mechanism is needed beyond the scheduler itself
- Outbound webhooks: one `company.slack_webhook_url` (nullable), Admin-only to configure via a new `/integrations/slack` endpoint gated on a new `company.configure` permission (Admin-only) — **not** the existing `company.update`, which turned out to be reserved for Super-Admin cross-tenant management of *other* companies (`/companies/{id}`, hard `require_super_admin` gate), the wrong semantic fit for a tenant Admin editing their own company's settings. `company.configure` follows the same "narrower than `.view`, granted only to Admin" pattern as `leave.configure`/`timesheet.configure`/`report.configure`. When a webhook URL is set, every event that already triggers an in-app notification (Leave, Timesheet, Assets, Onboarding, plus the two digest reminders above) also enqueues a Celery task that `POST`s a plain `{"text": "..."}` payload to that URL — a format both Slack incoming webhooks and Microsoft Teams connectors accept, though not either platform's richer native card layout. A fan-out event (e.g. onboarding submission notifying every HR reviewer) dispatches exactly one webhook message per event, not one per recipient — the shared channel doesn't need N duplicate pings for what's really one event.
- Webhook delivery is fire-and-forget via Celery — the same "Celery for slow/external I/O, not a general async-dispatch bus" pattern already established for email, so a dead or slow webhook URL never blocks or fails the request that triggered it, and the in-app notification (already persisted + pushed independently) is unaffected either way
- A "Send test message" action so an Admin can verify a newly-configured webhook URL actually works, in a small Admin-only **Integrations** page — no dedicated page for the digests themselves, since they just show up in the same bell every user already has

**Adjusted from the original scope**: birthdays and probation-period reminders are cut. Birthdays need a `birth_date` field that doesn't exist anywhere on `Employee` today — adding one is a real, separate scope decision (sensitive PII, and no onboarding UX currently collects it), not just a scheduling problem. "Probation" isn't a concept that exists anywhere in this app yet either (no field, no status, no onboarding step) — inventing one solely to power a reminder would be scope creep for a phase that's about *delivering* reminders from data that already exists, not creating new HR-tracking concepts. Slack/Teams payloads are kept to the plain-text format both platforms already accept, rather than building and maintaining two platform-specific rich-card payload builders for a first version. The permission gate (`company.configure` instead of the originally-planned `company.update`) was also adjusted once implementation revealed `company.update` is exclusively a Super-Admin cross-tenant action, never granted to any tenant role — see above.

## Phase 9a — Attendance *(shipped)*
- `attendance_shift_config`: one row per company (mirrors `timesheet_period_config`'s existing shape) — `shift_start`, `shift_end`, `grace_period_minutes` (default 15), used to compute late/overtime flags
- `attendance_record`: one row per employee per day — `check_in_at`, `check_out_at` (both nullable until they happen), `is_late` (computed at check-in against `shift_start + grace_period_minutes`), `overtime_hours` (computed at check-out against shift duration)
- Self-service, no special permission needed at all — not even a broadly-granted one the way `timesheet.create` is (there's no on-behalf-of concept for attendance to gate), same as `/leave-requests/mine`'s self-scoping: `POST /attendance/check-in`, `POST /attendance/check-out`, `GET /attendance/mine`
- Company-wide, gated on a new `attendance` permission module (`view`/`export`/`configure`, same shape as `leave`/`timesheet`): `GET /attendance` (filterable list), `GET /attendance/export` (CSV), `GET`/`PATCH /attendance/settings` (shift config, Admin-only via `configure`). Default grants: Admin gets view+export+configure, HR gets view+export, Manager gets view; Employee and Finance get none of the company-wide grants (attendance has no billing angle the way Timesheets does, and everyone already gets their own record via `/attendance/mine`)
- A new **Attendance** nav item with tabs mirroring Leave/Timesheet: **My Attendance** (check-in/out button + own history), **Today** (who's checked in/late/not-yet-in, for Manager/HR/Admin), **Company Attendance** (filterable history + export), **Settings** (shift config, Admin-only)
- Attendance becomes a 7th reportable module in the existing Reports hub (Phase 7), reusing the same `report_rows()` pattern every other module already follows

**Adjusted from the original scope**: no real GPS geofencing or QR scanning — check-in/out is just a button + server timestamp, consistent with the original scope's own note that GPS/QR/biometric are "external integration points, not built in-house." No per-department shift overrides — one shift schedule per company, like Timesheets' period config. No approval workflow — attendance is a factual log, like Assets, not something anyone approves. No "absent" record synthesis via a background job — absence is implicit (no row for that day) rather than a second scheduled job competing with Phase 7c's digest. Doesn't touch or merge with Timesheets — Attendance tracks *when* someone was present; Timesheets tracks *what* they worked on. Subscription/Billing is split out to Phase 9b, since it's a Super-Admin/platform-owner concern with no overlap in users or workflow with Attendance. One limitation surfaced during implementation, not originally called out: `check_in_at`/`check_out_at` are stored as UTC-aware timestamps but compared against the plain wall-clock `shift_start`/`shift_end` with no per-company timezone conversion — there's no timezone field anywhere in this app yet (Timesheets/Leave have the same gap), so late/overtime detection is only accurate for companies operating in UTC until a real per-company timezone field is added.

## Phase 9c — White-Label Onboarding Branding & Company Tour *(shipped)*
- `company.logo_key` (nullable, S3/MinIO object key, same private-bucket-plus-presigned-URL pattern as employee documents) and `company.primary_color` (nullable hex string), Admin-configurable via a new "Branding & Tour" tab on the existing Onboarding settings page, gated on the existing `onboarding.configure` permission — no new permission module needed, since this genuinely is onboarding-flow configuration
- `company_tour_step`: an Admin-authored, ordered list of simple slides (title, body text, optional image) shown to a new hire during onboarding — same company-scoped catalog shape as `document_type` (sort_order, no approval/versioning), CRUD gated on `onboarding.configure`
- Scope is deliberately narrowed to the **public onboarding experience only** (`/onboarding/{token}`, already unauthenticated and already has company context via the invite token) — not the authenticated internal app (dashboard, login page). The internal app is used daily by the company's own staff who already know it's a shared platform; a new hire's onboarding link is the one surface an outside person sees before they're a "user" of anything, so that's where branding actually matters. Full white-labeling of the entire internal app (custom domains, a per-tenant theme engine reachable pre-login) is a materially bigger, separate undertaking and out of scope here.
- The existing `GET /onboarding/{token}` response gains `company_branding` (name, presigned `logo_url`, `primary_color`) and `tour_steps` — no new public endpoint, just enriching the response the public onboarding page already fetches
- On the public onboarding page: the tour shows as a skippable, replayable stepper (Back/Next/Skip/Finish) *before* the existing password + document-upload steps, using `primary_color` as the accent on its buttons and the company logo in place of the generic "Employee Portal" header. Once dismissed it doesn't reappear on that same link (tracked client-side only, keyed by the onboarding token — no new "has seen tour" column), with a small link to replay it
- Not an embeddable widget for a company's own external website — embedding a real auth/onboarding flow via iframe on a third-party origin is fragile in practice (`X-Frame-Options`, cross-origin cookies) and isn't how most SaaS products solve this; a company that wants this on their careers page can simply link to their own on-brand onboarding URL

## Explicit Non-Goals for Phase 1 (superseded where later phases have shipped)
To keep Phase 1 a real, working slice rather than a wide shallow scaffold, the following were **not** built yet even though their tables/fields were reserved in the schema: onboarding workflow, document upload, projects, timesheets, leave, assets, reports, notifications beyond transactional email, biometric/GPS attendance, OAuth social login, MFA enforcement, AI features. Each has a clear landing phase above and none required breaking schema changes to the Phase 1 foundation. Onboarding workflow and document upload shipped in Phase 2 (above); the rest remain open per their listed phase.
